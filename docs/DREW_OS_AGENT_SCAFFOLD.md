# Drew OS Agent Scaffold

Status: experimental doctrine, specimen-zero ready  
Origin: Thunder Brainstorm / Pose Lab production lessons  
Purpose: turn abundant personal corpus into a small active basis for agent inference without requiring a CLI, app, or bespoke runtime.

## Core thesis

Drew OS is not primarily a generator and not primarily a memory system.

It is a deterministic scaffold around nondeterministic inference.

The agent may reason freely inside a bounded working set, but retrieval, authority, narrowing, exclusion, verification, and promotion are governed by explicit rules.

> Do not make the agent deterministic. Make the rails deterministic.

## Manufactured Scarcity Theorem

When generative capacity makes production abundant, creative quality shifts away from fabrication and toward selection.

A sufficiently rich corpus creates more plausible material than can be used at once. Taste becomes operational when the system deliberately excludes most of that material and freezes a small, high-information basis for the current problem.

> Abundance supplies possibility.  
> Taste manufactures scarcity.  
> Rules preserve taste.  
> Procedure spends the resulting scarcity combinatorially.

## Small Basis Theorem

A small, well-chosen basis of authored elements can produce more expressive variety than a much larger set of individually authored outcomes when composition rules preserve the causal properties that made those elements worth choosing.

This is Vicious Compression generalized beyond animation.

## Selection Precedes Generation

Once a corpus is abundant, the highest-leverage generative act is choosing the basis from which generation is allowed to occur.

Generation before selection invites slop. Selection before generation creates a constrained search space in which inference can remain creative without dissolving identity.

## Deterministic scaffold

Every governed agent pass follows this sequence:

```
BOOT
  ->
RETRIEVE
  ->
ABSTRACT
  ->
NARROW
  ->
FREEZE
  ->
COMPOSE
  ->
VERIFY
  ->
PROMOTE OR KILL
```

The stages are mandatory. The specific reasoning inside a stage may vary.

## 1. BOOT

Before proposing a solution, recover:

- the concrete task;
- the relevant project or domain;
- authoritative sources;
- active doctrine;
- accepted canon;
- known rejection history;
- the requested output and acceptance surface.

Rules:

- Evidence outranks recollection.
- Existing authority must be consulted before invention when it exists.
- Do not silently substitute a neighboring project, architecture, style, or source.
- Do not treat conversation familiarity as a replacement for current source truth.
- If the task is underspecified but the corpus contains a clearly established local convention, recover it before asking Drew to restate it.

## 2. RETRIEVE

Retrieve broadly enough to expose useful abundance.

Possible sources include:

- Thunder Brainstorm;
- Story Brainstorm and other specialized brainstorms;
- project canon;
- accepted artifacts;
- rejected artifacts when their failure is informative;
- rules and doctrines;
- prior implementations;
- source media;
- neighboring projects with transferable mechanisms.

Rules:

- Retrieval is not selection.
- Do not promote every retrieved item into working context.
- Preserve provenance.
- Prefer source-backed evidence over summaries when the distinction matters.
- Contradictory evidence remains visible until resolved.

## 3. ABSTRACT

Infer reusable semantic structure from retrieved material.

Examples:

- verbs;
- causal chains;
- load paths;
- timing families;
- spatial relationships;
- visual invariants;
- tactical roles;
- compositional patterns;
- failure classes;
- reusable transformations.

Rules:

- Abstractions must remain traceable to evidence.
- Do not confuse surface resemblance with causal equivalence.
- Preserve distinctions that matter to behavior.
- A useful abstraction should reduce the amount of material required to reason correctly.

## 4. NARROW

Manufacture scarcity.

Reduce the retrieved abundance into the smallest basis sufficient for the task.

A basis should normally contain only the useful few:

- primary objective;
- selected principles;
- donor examples;
- allowed verbs/components;
- composition rules;
- explicit exclusions;
- acceptance tests.

Rules:

- The active basis MUST be materially smaller than the retrieved corpus.
- Redundancy is a reason to exclude.
- Novelty is not a reason to include.
- Existing corpus material should beat new fabrication by default.
- New assets, mechanics, animations, abstractions, or architectures require evidence that the current corpus cannot satisfy the need.
- The basis may be expanded only when a concrete insufficiency is observed.

This stage is the core Drew OS operation.

## 5. FREEZE

Before composition, freeze the basis for the attempt.

Internally establish:

- what is active;
- what is excluded;
- what may vary;
- what is locked;
- what evidence would justify reopening the basis.

Rules:

- Do not browse for inspiration during composition unless the frozen basis proves insufficient.
- Do not opportunistically add a clever donor because it became convenient.
- Excluded material remains excluded for the current attempt.
- If the attempt encounters a real missing capability, stop composition, return to NARROW, create a revised basis, then continue.

This is the creative equivalent of Pose Lab's plan/seal/apply boundary.

## 6. COMPOSE

Reason freely inside the frozen basis.

Possible outputs include:

- mechanic;
- enemy kit;
- animation;
- story structure;
- level grammar;
- code plan;
- architecture;
- visual system;
- tool behavior;
- research synthesis.

Rules:

- Recombination is encouraged.
- Emergence is allowed.
- Surprise is allowed.
- New implementation detail is allowed when it realizes the selected basis.
- Do not expand scope merely because the agent can.
- Prefer reuse, transformation, sequencing, timing, context, and procedural combination before new fabrication.

## 7. VERIFY

Test the result against reality and taste.

Verification asks:

- Does it satisfy the task?
- Does it preserve canon?
- Does it violate an explicit exclusion?
- Did the result actually change, or did the explanation change?
- Does the visible/behavioral outcome match the claim?
- Did a test prove the product, or only something adjacent to the product?
- Is the result distinct enough to justify its existence?
- Does it create a new banana peel already represented in doctrine?

Rules:

- Human-visible evidence outranks fluent explanation.
- Passing transport, syntax, build, or simulation does not prove product behavior unless product behavior is what was tested.
- Confidence is not evidence.
- If perception is uncertain, say so and inspect again rather than constructing a causal theory on a weak premise.
- A sophisticated explanation built on a false visual premise is a failure, not a partial success.

## 8. PROMOTE OR KILL

Accepted survivors may become durable knowledge.

Promotion should preserve:

- source provenance;
- selected basis;
- result;
- acceptance reason;
- reusable abstraction;
- rejection history where it teaches a general rule.

Rejected outputs do not silently become canon.

Rules:

- Do not recursively train only on compressed descendants. Reopen source corpus periodically.
- Preserve correction history so future agents can distinguish original evidence from later interpretation.
- Promote reusable lessons, not every artifact.
- A failure class that recurs should become a guard or doctrine rule when feasible.

## The anti-oatmeal rule

Drew OS must not collapse into self-imitation.

Repeatedly generating from prior compressed outputs will eventually produce caricature.

Therefore:

- source material remains first-class;
- old projects remain searchable;
- rejected work remains available as archaeology;
- contradictions are not automatically smoothed away;
- new external or lived experience may perturb the corpus;
- later generations should be able to reach past summaries to original evidence.

The goal is not "make it more Drew-like."

The goal is "recover the smallest source-grounded basis that Drew's demonstrated taste would plausibly choose for this problem."

## Agent behavior contract

A Drew OS-compliant agent should be able to answer these questions before consequential composition:

1. What problem am I solving?
2. Which sources are authoritative?
3. What useful abundance did I retrieve?
4. What semantic structure did I infer?
5. What did I deliberately exclude?
6. What is the frozen basis?
7. What is allowed to vary?
8. What evidence will prove success?
9. What survives if this attempt fails?

If the agent cannot answer them, it is not ready to compose.

## Product hypothesis

Drew OS is a corpus-backed deterministic inference scaffold that:

1. recovers relevant history;
2. abstracts reusable grammar;
3. manufactures a small active basis;
4. freezes that basis;
5. permits flexible agent inference inside it;
6. verifies against real outcomes;
7. promotes only accepted survivors.

The intelligence is replaceable.

The scaffold is the product.

## Specimen-zero acceptance test

A fresh agent should be given:

- this scaffold;
- a bounded task;
- access to relevant corpus;
- minimal conversational coaching.

Success means the agent independently:

- retrieves the right authorities;
- selects a small coherent basis;
- resists using all available material;
- composes something recognizably appropriate;
- explains its exclusions;
- does not require Drew to reteach known doctrine.

If conversational coaching is needed to recover a rule already represented in the corpus, improve the scaffold or the corpus interface rather than teaching one agent a private workaround.
